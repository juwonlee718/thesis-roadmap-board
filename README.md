# 논문길 · 졸업논문 진행 보드

전공마다 다른 졸업논문 절차에서 현재 단계와 다음 할 일을 확인하고, 학생·교수·행정실이 같은 진행 상태를 보는 브라우저 데모입니다. 대표 흐름은 **다전공 학생의 지도교수 승인 요청 → 교수 승인 → 행정실 확정 검토 → 모든 역할 화면 반영**입니다.

## 실행 방법

Node.js 22.12 이상인 22.x 또는 24.x(이 작업에서는 24.17.0), npm을 사용합니다. Vitest 5의 실행 요건을 포함한 버전 기준입니다.

```bash
npm ci
npm run dev
```

브라우저에서 `http://127.0.0.1:3000`을 엽니다. 시작 화면 `/`, 학생 `/student`, 교수 `/professor`, 행정실 `/admin`을 제공합니다. 상단 역할 탭으로 전환하고 각 화면의 데모 사용자를 선택합니다.

프로덕션 실행:

```bash
npm run build
npm run start
```

Next.js App Router, TypeScript, Tailwind CSS, Zustand persist를 사용합니다. Vercel의 Next.js 기본 빌드 설정으로 빌드할 수 있는 구조이며 **외부 공개·배포는 수행하지 않았습니다**. 기존 `dist/` 정적 프로토타입과 `.openai/hosting.json`은 보존했으며 새 Next.js 앱의 실행 경로가 아닙니다.

## 저장과 역할 공유

- 로그인·DB·외부 API·API 키·`.env`가 없습니다. 서체와 이미지도 외부 서비스를 호출하지 않습니다.
- 상태는 `localStorage`의 `thesis-board-v1`에 저장됩니다. 같은 브라우저의 같은 출처에서 역할 전환·새로고침 후에도 유지됩니다.
- 같은 출처의 다른 탭에는 `storage` 이벤트로 변경 내용을 반영합니다. 다른 브라우저·기기 사이의 실시간 공유는 지원하지 않습니다. 동시 편집 충돌은 마지막 저장이 우선합니다.
- 우측 상단 **데모 초기화**로 모든 학생·교수·이력을 seed로 되돌립니다. 대표 학생은 전공 입력 전으로 돌아갑니다.
- 모든 도메인 상태 변경은 변경자·한국 시각·내용·대상 학생/학과를 이력에 기록합니다. 초기화는 이력까지 seed로 복원하는 예외입니다.

## 가상 데이터와 가정

모든 절차·날짜·인물·문의처는 가상입니다. 실제 학교 공지를 수집하지 않았고 실제 개인정보를 사용하지 않았습니다. 모든 학과에 **예시 데이터**, 공식 링크에 **예시 링크(가상)**를 표시합니다. 문의 이메일은 발송할 수 없는 예약 도메인 `example.invalid`를 사용합니다.

| 학과       | 지도교수 방식             | 정원   | 주전공 / 복수전공 |
| ---------- | ------------------------- | ------ | ----------------- |
| 심리학과   | 직접 컨택 후 승인 요청    | 미적용 | 필수 / 필수       |
| 기계공학과 | 전공 수업에서 행정실 배정 | 미적용 | 필수 / 필수       |
| 사회학과   | 시스템 신청 후 교수 승인  | 적용   | 필수 / 면제       |

- 마감은 2026년 9–12월의 가상 날짜이며 마감일 전체를 기한으로 표시합니다. 캘린더의 한 주는 월요일에 시작합니다. 같은 주에 다른 전공의 미완료 마감이 있으면 경고합니다.
- 교수 승인 시 해당 전공의 현재 단계만 다음 단계로 이동합니다. 지도교수 단계는 **검토 대기**로 남으며 행정실 **검토 완료**로 최종 완료됩니다. 다른 전공 단계는 유지됩니다.
- 확정 전에도 다음 서류를 준비·기록할 수 있습니다. 행정실 보완 요청 상태에서는 해당 전공의 일반 제출 기록을 막고, 보완 내용을 작성해 재검토 요청하도록 했습니다.
- 최종 결과 완료 처리는 지도교수 확정 검토까지 완료된 후 가능합니다.
- 수정 요청·면담 요청·반려 후 학생은 연구 주제와 계획을 입력해 재신청할 수 있습니다. 기존 결정과 피드백은 변경 이력에 남습니다.
- 수업 배정은 행정실이 수강 사실도 함께 확인한 것으로 가정하여 수강·배정 확인 단계를 완료합니다. 수업 방식에는 학생 신청 버튼이 없습니다.
- 정원 미적용 학과의 정원용 배정 카운터는 변경하지 않습니다. 교수 화면의 승인·배정 학생 수는 신청 기록에서 계산합니다.
- 실제 파일 업로드나 이메일 발송 없이 **제출 완료 기록**만 저장합니다. 최종 결과 단계는 행정실이 완료합니다. 서식은 화면에서 구조를 보여주는 가상 안내입니다.
- 이미 진행 중인 전공 설정을 바꾸어 이력을 잃지 않도록, 전공 재설정은 데모 초기화 후에만 가능합니다.
- `docs/student.md`, `docs/professor.md`를 참고했습니다. 요청에 언급된 `docs/admin.md`는 작업 시작 시 없었으므로 행정실은 이번 요청의 명시 요구사항을 기준으로 구현했습니다. AGENTS.md와 docs 파일은 수정하지 않았습니다.

## 사용자 테스트 진행 질문

**사람이 수행할 검증이며 아직 결과가 없습니다.** 3분 리허설, 전공 입력 후 1분 이내 절차 이해, 참여자 5명 중 4명 이상 다음 할 일 정답 여부를 에이전트 완료 결과에 포함하지 않습니다.

1. 전공을 입력한 직후, “지금 가장 먼저 해야 할 일은 무엇이고 언제까지인가요?”
2. “두 전공의 지도교수 결정 방식은 어떻게 다른가요? 직접 신청하지 않는 전공은 어느 쪽인가요?”
3. “같은 주에 마감이 겹치는 일은 무엇인가요? 제출 방법과 서식, 문의처는 어디서 확인하나요?”
4. 교수 승인 직후, “어느 전공이 다음 단계로 이동했나요? 지도교수 확정은 끝났나요?”
5. “수정 요청이나 보완 요청을 받으면 어디에서 내용을 확인하고 무엇을 해야 하나요?”
6. 행정실 검토 완료 후, “최종 확정되었다는 것을 어디서 알 수 있나요?”
7. “정원이 찬 교수에게 신청할 수 있나요? 이 정보가 충분히 눈에 띄나요?”

진행자는 답을 유도하지 않고 첫 답변과 소요 시간, 클릭 경로, 막힌 지점을 익명으로 기록합니다. 초기 대표 학생의 정답은 “기계공학과 졸업논문 수업 수강, 2026-09-24까지, 수업에서 확인”입니다. 1분 후 절차 설명과 다음 할 일 정답을 따로 판정하며, 5명 중 4명 이상의 정확한 첫 답변 여부를 집계합니다.

## 학과 데이터 교체 방법

1. 실제 정보가 제공되면 `docs/departments/*.md`의 내용과 제공된 공식 URL을 확인합니다. 문서 원본 변경은 별도 승인을 받습니다.
2. `data/departments/*.ts`에서 학과 이름·학기·출처·확인일·링크·주/복수전공 요건·지도교수 방식·정원 여부·단계 정보를 교체합니다. 새 학과는 파일을 추가하고 `data/departments/index.ts` 배열에 등록합니다. 화면 컴포넌트를 고치지 않습니다.
3. 각 단계는 고유 `id`, `name`, `kind`, `deadline`, `description`, `documents`, `form`, `submission`, `evidence`, `notice`, `contact`를 갖습니다. 지도교수 단계는 `kind: 'advisor'`로 지정합니다. `course`는 수강 기록, `submission`은 학생 제출 기록, `result`는 행정실 최종 결과 확인입니다. 단계 순서는 배열 순서를 따릅니다.
4. 주전공·복수전공 요건은 각각 `필수` 또는 `면제`로 입력합니다. `advisorMethod`는 `contact_approval`, `application`, `course_assigned` 중 하나입니다. 실제 링크를 받지 않았다면 `예시 링크(가상)`을 유지합니다. 일부만 실제 정보이면 `일부 가정`으로 표시합니다.
5. seed 시연 학생·교수의 소속이 변경된 학과 ID와 일치하도록 `data/seed.ts`의 합성 데이터를 조정합니다. 저장된 이전 로드맵을 사용하는 브라우저는 **데모 초기화**합니다. 별도 데이터 마이그레이션은 제공하지 않습니다.
6. `npm test`, `npm run build`, `npm run test:e2e`를 실행합니다. 현재 완결성 테스트의 학기 범위는 2026-2학기(9–12월)입니다. 다른 학기에 실제 사용하는 경우 범위 변경 승인을 받고 검증 조건도 해당 학기로 갱신해야 합니다.

요건·공식 링크·마감일이 비면 완결성 테스트가 실패합니다. 런타임 화면은 빈 값을 **정보 확인 필요**로 표시합니다. 테스트는 누락된 값 세 가지를 실제 화면 컴포넌트에 넣어 생성한 별도 HTML에서도 이를 확인합니다. 이 검증 fixture는 정상 학과 데이터나 사용자 저장 상태에 섞이지 않습니다.

## 검증 명령과 산출물

```bash
npm run test
npm run build
npx playwright install chromium
npm run test:e2e
npm run typecheck
```

E2E는 프로덕션 빌드 서버를 자동 실행하므로 3000 포트가 비어 있어야 합니다. `npm run test`가 누락 정보 화면 fixture를 생성하므로 위 순서를 지켜 주세요. PC 1440px 및 모바일 390px Chromium 프로젝트에서 같은 흐름을 실행합니다.

- `tests/rules.test.ts`: 학과 기반 생성, 면제, 다음 할 일, 겹침, 정원, 피드백, 전공별 상태 전이, 수업 배정, 제출 담당자 검사
- `tests/data.test.tsx`: 학과 완결성 검사와 누락 정보 표시 fixture 생성
- `tests/e2e/board.spec.ts`: 대표 흐름, 수정 요청/반려의 즉시 반영, 정원 차단, 보완 재검토, 수업 배정, 면제, 누락 정보 표시, 가로 넘침 검사
- `output/playwright/`: PC·모바일 화면 캡처와 누락 정보 fixture
- `playwright-report/`: 최신 HTML E2E 결과(자동 생성, git 제외)
